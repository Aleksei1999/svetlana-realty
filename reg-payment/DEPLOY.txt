Run private/initialize.php with /opt/php/8.3/bin/php; it never overwrites an existing config.
Config, database and sessions must never be committed or uploaded to the public website.

Webhook URL: https://www.xn--80ajklwp.site/api/index.php?action=webhook
YooKassa events: payment.succeeded, payment.canceled, payment.waiting_for_capture.
Every event triggers an authenticated GET to YooKassa; the event body is never proof of payment.
The browser status endpoint requires the order owner's secure session and a CSRF token.
Payment amount is fixed server-side: 4990.00 RUB. A client-supplied amount is ignored.

Before enabling:
- Configure secret_key privately on the server, and the matching shop_id/mode.
- Configure actual merchant receipt VAT/payment_mode/payment_subject; examples in tests are fixtures only.
- Verify a TEST-shop payment before enabling live sales.
- Publish merchant-approved offer/privacy/consent documents and configure their URLs/version.
- Complete fulfillment (Telegram bot) before setting fulfillment_ready=true.
- Set enabled=true only after the other production gates are satisfied.
- Configure YooKassa notifications in the authenticated merchant dashboard.

No YooKassa credentials or bot credentials are included.
Telegram fulfillment is implemented in private/telegram.php and action=telegram.
Runtime telegram-token.txt and telegram-config.json remain outside webroot, mode 0600.
After install and passing tests, run private/telegram-setup.php from its deployed directory.
REG.RU inbound Telegram requests timed out in verification; use polling on this hosting:
Run telegram-setup.php --poll, then install a per-minute cron for private/telegram-poll.php.
The poller uses outgoing IPv6, keeps a private persistent update offset, and never acknowledges
a failed update. It holds a separate worker lock so jobs cannot overlap. Normal latency is up to a minute.
It checks the configured bot and administrator invitation rights, creates a private webhook secret,
and registers the HTTPS webhook. It does NOT enable YooKassa sales or mark fulfillment_ready.
Incoming updates require the exact Telegram secret header. Duplicate updates are recorded.
The payment owner's browser alone receives an opaque bot claim link, after a verified live success.
Opening that link only proposes a Telegram account. Buyer must explicitly confirm its numeric ID
from their original secure website session. Before both invitation and joining, a fresh authenticated
YooKassa GET must confirm the exact order/shop/amount/currency, succeeded, paid, non-test, no refund.
15-minute invitations request approval; only the bound Telegram ID is approved; link then revoked.
A provider outage gives no invitation/approval and retries preserve binding and existing invitation.
Test payments cannot unlock this production chat; use mocked test suite or a separately isolated
staging bot/chat for provider sandbox end-to-end validation. Never insert fake paid orders into production.
Existing manual invite links/admin approvals are outside this workflow.
Automatic removal after 3 months is not implemented; new invitations are blocked after expiry.
Bot recovery from buyer losing their original browser session requires manual organizer support.
Before launch, verify a real provider test flow in isolated staging and the final live configuration.
Refunds are handled in YooKassa; automatic access revocation for refunds is not implemented yet.
